# Диагностика конструктора наборов (K01)

Дата: 2026-10-28
Ветка: `dev`-подобная рабочая копия на коммите `4385832` + незакоммиченные правки в двух файлах.
Задача: установить, почему конструктор наборов не работает, не меняя код в `azbuka-src`.

## 1. Симптом

Родитель заходит в «Настройки → Мои наборы» и видит «Пока нет своих наборов», хотя наборы в
хранилище есть. Если создать набор прямо на этом экране, строка появляется; после выхода и
повторного входа список снова пуст. Ранее созданные наборы «пропадают» из списка, но файлы
на диске остаются.

## 2. Как воспроизведено

Воспроизведение сделано на настоящей сцене `res://ui/constructor/set_list/set_list.tscn`
с настоящим автолоадом `CustomSetsStore`, без моков: сцена инстанцируется в headless-прогоне,
в хранилище заранее лежат два набора, после одного кадра читается `get_row_count()`
и подпись первой строки.

Проба (`tests/probe_set_list.gd`, живёт только в скретч-воркtree, в репозиторий не входит):

```gdscript
extends Node

func _ready() -> void:
	await get_tree().process_frame
	CustomSetsStore.save_path = "user://probe_sets.json"
	CustomSetsStore.clear_memory()
	CustomSetsStore.save_sets()
	var a := CustomSetsStore.create_set("Альфа")
	var b := CustomSetsStore.create_set("Бета")
	var list: Node = load("res://ui/constructor/set_list/set_list.tscn").instantiate()
	add_child(list)
	await get_tree().process_frame
	await get_tree().process_frame
	print("PROBE rows_on_open=", list.get_row_count())
	var row: Node = list.get_row(0)
	var label := row.get_node_or_null("%NameLabel") as Label
	print("PROBE row0_name=", "<nil>" if label == null else label.text)
	var c := CustomSetsStore.create_set("Гамма")
	await get_tree().process_frame
	print("PROBE rows_after_create=", list.get_row_count())
```

Запуск (чистый пользовательский каталог: имя проекта в скретч-копии переименовано,
чтобы `user://` не пересекался с данными ребёнка):

```
godot --headless --path <copy> res://tests/probe_set_list.tscn
```

Контроль: те же файлы, но без незакоммиченных правок (`git checkout -- ui/constructor/set_list/`).

## 3. Результаты

| Прогон | Наборов в хранилище до открытия | `rows_on_open` | Имя первой строки | `rows_after_create` |
|---|---|---|---|---|
| HEAD `4385832` (эталон) | 2 | **2** | «Альфа» | 3 |
| рабочая копия (с правками) | 2 | **0** | — | 3 |
| ветка `fix/constructor-mobile-recording` `d336d11` | 2 | **2** | «Альфа» | 3 |

Логи: `evidence-20261028/probe_head2.log`, `evidence-20261028/probe_dirty2.log`,
`evidence-20261028/probe_fix.log`.

Совпадение «0 при открытии, 3 после создания» объясняет наблюдаемое поведение: строка
появляется только потому, что `create_set()` эмитит `sets_changed`, а `_ready()` к этому
сигналу подписан. Сам список при открытии не перечитывается.

## 4. Причина

`ui/constructor/set_list/set_list.gd`, функция `_ready()`. В HEAD последней строкой было:

```gdscript
	CustomSetsStore.sets_changed.connect(refresh)
	refresh()
```

В рабочей копии вызов `refresh()` **удалён** (осталась только подписка на сигнал):

```gdscript
	if CustomSetsStore and CustomSetsStore.sets_changed and not CustomSetsStore.sets_changed.is_connected(refresh):
		CustomSetsStore.sets_changed.connect(refresh)
```

`refresh()` — единственное место, где `_rows` заполняется из `CustomSetsStore.get_sets()`
и где `_empty_label.visible` выставляется по факту наличия строк. Без вызова из `_ready()`
при открытии сцены: `_rows` пуст, `_empty_label` остаётся видимым по умолчанию
(в `set_list.tscn` у `EmptyLabel` нет `visible = false`), а подписка на `sets_changed`
срабатывает только на последующие изменения.

Остальные правки в этом же дифе (`if _new_button and ...`, проверки `is_connected`) —
оборонительные и на поведение не влияют: `@onready`-поля к моменту `_ready()` уже заданы.

| `azbuka-constructor-fix/` | `d336d11` | ветка `fix/constructor-mobile-recording`, **на 3 коммита впереди** `4385832`; `refresh()` в `_ready()` на месте, проба даёт 2 строки |

Коммиты, которых нет в `azbuka-src`: `2a4d163` (фолбэк на встроенные данные,

## 5. Что НЕ подтвердилось

Гипотеза «`SetListRow.setup()` вызывается до `add_child()`, поэтому `@onready`-поля `nil`» —
**ложна** для текущего кода. В `refresh()` порядок правильный:

```gdscript
		var row: SetListRow = ROW_SCENE.instantiate()
		_scroll.add_child(row)          # здесь же отрабатывает _ready() строки
		row.setup(name, open_count, is_complete)
```

Проверка: в прогоне на HEAD первая строка показывает имя «Альфа», то есть `setup()` доезжает
до `Label`. Оборонительные `if _name_label` в `set_list_row.gd` маскируют ошибки, но ничего
не ломают.

## 6. Почему это не поймали тесты

`tests/validate_constructor_ui.tscn` в чистом окружении проходит **и на HEAD, и на рабочей
копии**: `206 проверок успешны` в обоих прогонах (`evidence-20261028/ui_head_cleanenv.log`,
`evidence-20261028/ui_dirty_cleanenv.log`). Причина: валидатор сам вызывает `refresh()`
после каждого действия и не проверяет сценарий «в хранилище уже есть наборы, сцену только
открыли». Единственная проверка `_ready()` у списка (`_check_set_list_ready_ran`) смотрит
подписки, кнопку и стили, но не число строк.

Побочное наблюдение: тот же валидатор **не идемпотентен** относительно `user://`. Первые
прогоны на загрязнённом каталоге дали 13–14 падений в блоке SetList (строки из прошлых
прогонов подмешивались в «пустое» хранилище). В чистом каталоге — 206/206. Это дефект теста,
а не приложения, но он умеет маскироваться под регрессию.

## 7. Сопутствующие дефекты (найдены по коду, вне причины выше)

1. **Прослушивание не-WAV файлов в редакторе не работает.**
   `ui/constructor/set_editor/set_editor.gd:318-326`: `_on_play_requested()` всегда делает
   `AudioStreamWAV.new()` и кладёт в него сырые байты файла. Для `mp3`, `m4a`, `ogg` это
   не WAV-контейнер: поток молчит или играет мусор. При этом игры читают те же файлы
   корректно — `systems/set_repository.gd:173-177` выбирает `AudioStreamWAV` /
   `AudioStreamOggVorbis` / `AudioStreamMP3` по расширению. Тест проверяет только то, что
   mp3 не переименован в `.wav`, а тип потока при `play_requested` не проверяет.
2. **Нет регрессионного теста на открытие списка с готовыми наборами** (см. п. 6).
3. **Валидатор зависит от состояния `user://`** (см. п. 6): при падении посередине
   остаются тестовые наборы, следующий прогон падает в начале блока SetList.
4. **Шум в самом тесте:** `tests/validate_constructor_ui.gd:681` — строка формата с `%`,
   но без аргументов (`String formatting error` в логе). На результат не влияет, но это
   ошибка в тестовом коде.
