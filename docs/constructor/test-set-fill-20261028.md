# Инструмент наполнения тестового набора

Дата: 2026-10-28
Ветка: test/fill-test-set
База: azbuka-v2, HEAD 3a5b5cd
Статус: реализовано, проверено, применено к реальным данным

## Зачем

Ручная проверка конструктора требует набора, в котором у 33 букв уже есть слово,
картинка и звук. Заполнять его через нативные диалоги долго, а ошибки пикера при
этом смешиваются с ошибками самого конструктора. Инструмент берёт те же данные,
которые игра показывает в наборе 1, и раскладывает их в пользовательский набор
так же, как это делает редактор.

Инструмент не меняет игру и не включён в обычный запуск. Это отдельная сцена
`tools/fill_test_set.tscn`, которая работает только из командной строки.

## Запуск

Из корня проекта:

```sh
godot --headless --path . tools/fill_test_set.tscn -- --name="Тестовый набор"
```

Заполнить только три буквы и выгрузить исходники для ручной проверки пикера:

```sh
godot --headless --path . tools/fill_test_set.tscn -- \
  --name="Тестовый набор" --letters=А,Б,В --reset --export-dir=~/azbuka-export
```

Флаги:

| Флаг | Смысл |
|------|-------|
| `--name=...` | Имя набора. По умолчанию `Тестовый набор` |
| `--set-id=...` | Точный id. Сильнее имени |
| `--letters=А,Б,В` | Только эти буквы. Пустое значение означает весь алфавит |
| `--reset` | Удалить найденный набор и создать заново |
| `--export-dir=...` | Копировать исходные PNG и звук под именами `Буква_Слово` |

Неизвестный флаг это ошибка, а не молчаливое заполнение всего алфавита.

Коды возврата:

- 0: все запрошенные буквы записаны и проверены;
- 1: ошибка аргументов, ошибка создания набора или хотя бы одна буква не прошла
  проверку.

## Что именно пишется в набор

- Картинка: PNG из `res://assets` декодируется и сохраняется настоящим WebP через
  `ImageSaver`, имя `img_<translit>.webp`.
- Звук: байты исходного файла копируются без перекодирования, расширение
  сохраняется, имя `aud_<translit>.<ext>`.
- Метаданные: слово, относительный путь картинки и относительный путь звука через
  `CustomSetsStore.set_entry`. Префикс `user://` и абсолютные пути запрещены,
  потому что их не переносит веб-сборка и копирование данных.
- Проверка: `is_entry_complete`, `get_entry`, наличие обоих файлов. Проверяется
  то, что увидит игра, а не только факт записи.

Повторный запуск обновляет набор с тем же именем и не создаёт дубль. Если имён
несколько, берётся первый и печатается предупреждение, чтобы не удалить чужую
работу.

## Изоляция прогонов

Игра и валидаторы запускались только в копии:

```sh
rsync -a --exclude .git --exclude .godot --exclude .import ./ /tmp/azbuka-fill-set/
```

В копии `config/name` равен `Азбука-fill-set`, поэтому `user://` не совпадает с
реальным каталогом `Азбука`. Дополнительно каждый запуск шёл с отдельным `HOME`:

```sh
HOME=/tmp/azbuka-fill-suite-home godot --headless --path /tmp/azbuka-fill-set ...
```

Нужны оба барьера. Проверка `HOME` подтверждена: после запуска данные появились в
`/tmp/azbuka-fill-suite-home/Library/Application Support/Godot/app_userdata/Азбука-fill-set`,
а не в домашнем каталоге.

Импорт ресурсов в копии:

```sh
godot --headless --import --path /tmp/azbuka-fill-set
```

Код возврата 0. В `import.log` оставлен хвост: полный вывод импорта это 2206 строк служебного текста Godot, к результату он отношения не имеет.

## Валидатор

Валидатор подменяет `CustomSetsStore.save_path` и `ProgressManager.save_path` на
`user://custom_sets_fill_test.json` и `user://progress_fill_test.json`, заполняет
А, Б, В, проверяет метаданные, декодирует WebP и WAV, проверяет `is_custom` в
`SetRepository.get_word_data`, повторяет прогон и требует тот же id, затем удаляет
набор и оба тестовых JSON.

Финальный прогон:

```sh
HOME=/tmp/azbuka-fill-suite-home godot --headless --path /tmp/azbuka-fill-set \
  res://tests/validate_test_set_fill.tscn
```

Результат: exit 0, `PASSED: 73 проверок`, набор `c_e536d5` создан и удалён,
тестовые JSON удалены. Лог: `validate_test_set_fill_recheck.log`.

## Инцидент изоляции

Первый прогон инструмента для сбора доказательств был выполнен до того, как копия
получила отдельный `HOME`. Перед этим повторный `rsync` вернул в копию
`project.godot` с исходным `config/name="Азбука"`, поэтому Godot взял реальный
пользовательский каталог. В результате в реальном `custom_sets.json` появился
набор `c_a7b54d` "Тестовый набор" и 33 пары медиафайлов, а Godot повернул свои
логи.

Что восстановлено:

- `c_a7b54d` и его каталог удалены;
- `custom_sets.json` записан обратно в побайтово прежнем виде, sha256 совпал с
  зафиксированным до прогонов;
- созданный ранее каталог `app_userdata/Азбука-fill-set` удалён;
- новые логи аварийного прогона удалены.

Что восстановить нельзя: два старых лога Godot (`godot2026-10-28T18.10.46.log` и
`godot2026-10-28T19.18.25.log`) были вытеснены ротацией, содержимое `godot.log`
перезаписано. Это логи, не данные наборов и не прогресс. Пользовательский набор
`c_8c3b33` и его файлы не изменялись.

После инцидента все прогоны шли с двумя барьерами: `config/name="Азбука-fill-set"`
и отдельный `HOME`. Финальная проверка подтвердила, что реальный `custom_sets.json`
не изменился.

## Ограничения

- Инструмент использует встроенный набор слов 1 и его картинки и звуки. Если
  ресурс удалить, соответствующая буква попадёт в ошибки, остальные запишутся.
- Выгружаются исходные PNG и звук, а не WebP из набора. Это сделано для ручной
  проверки нативных диалогов.
- Инструмент не трогает прогресс, настройки и активный набор.
- Сеть не используется.
- Изменений в `systems/`, `ui/`, `assets/` и существующих тестах нет.
